# Project proposal: Faultline

**Course:** Advanced Algorithm (Semester V, B.Tech CS AI & ML), CIA 3, 2026–27
**Team:** _Name 1 (ID)_, _Name 2 (ID)_, _Name 3 (ID)_

## Real-world problem
Most account takeovers start with a password that is already in a public breach list or is built
from predictable pieces: a name, a year, a keyboard walk, or `p@ssw0rd`-style substitutions. IT
administrators need to find these passwords across an organisation, and individuals need to know
*why* a password is weak, not just a coloured bar. Checking against a million leaked passwords
must be fast and memory-light, and it must never wrongly tell a user their password is safe.

## Target users
- **College or company IT administrators** auditing exported password lists (one per line, or
  `username,password` CSV) before a policy rollout.
- **Individual users** checking a password before they use it.

## Proposed features
1. Single-password check: breach status, leak frequency rank, highlighted weak segments, strength
   score with entropy estimate, per-stage timings and concrete advice.
2. Batch audit of up to 10,000 rows: breach rate, password reuse across accounts, strength
   distribution, pattern-category counts and per-row results with masked passwords.
3. Built-in benchmark page comparing each algorithm with a baseline on three input sizes.
4. Validation of empty, oversized, non-UTF-8 and malformed input, with clear error messages.
5. Attack simulation for an organisation: upload accounts (`username,role,department,password`) and access (`from,to`), choose an attacker (online, bcrypt, SHA-1 on a GPU), a time budget and organisation terms. A best-first cracking race times when each account falls; max-flow on the access graph then names the smallest set of accounts to secure so a chosen system (e.g. Payroll DB) is out of reach, with the time to reach it before and after.

## Core techniques and why each fits
| Technique (syllabus unit) | Role | Why it is appropriate |
|---|---|---|
| **Bloom filter** (Unit 6, CO5) | In-memory precheck of SHA-1 hashes of 1M leaked passwords | No false negatives, so a miss is safe to trust. It uses about 1.2 MB instead of about 85 MB for a hash set and skips the disk for the large majority of passwords that are not leaked. Hits are only "possibly leaked" and are confirmed exactly by binary search over a sorted hash file. |
| **Trie** (Unit 4) | Finds every dictionary word, name, year, keyboard walk or common password inside a password, including leetspeak | A single walk per start position costs O(ℓ·L) regardless of dictionary size, against O(D·ℓ·L) for checking each word. |
| **KMP** (Unit 4) | Finds the username in the password; its prefix function detects repeated blocks (`abcabc`) | Linear-time matching with no worst-case blow-up. The same prefix function also yields the smallest period. |
| **Aho–Corasick** (Unit 4) | Finds every credential cue and key format in shared text so the secrets after them can be redacted | One pass over the text in O(n + matches) for any number of patterns, against one KMP pass per pattern. |
| **Binary heap** (Unit 2) | Orders an attacker's guesses (base word × mangling rule) from most to least likely in the attack simulation | Walking the sorted base × rule grid with a max-heap yields the next most likely guess in O(log h), with no visited set. Best-first guessing cracks 288 of 1,000 synthetic accounts in 5M guesses where brute force cracks none. A second Bloom filter skips repeated guesses in about 50× less memory than a HashSet. |
| **Max-flow / min-cut, Edmonds–Karp** (Unit 5) | Finds the fewest accounts to secure so that no cracked account can reach a protected system | Exact and polynomial (O(V·E²)) where trying subsets is exponential. Vertex capacities model "secure this account"; the residual graph names the accounts. |

Support: SHA-1 (JDK `MessageDigest`) and a dynamic program that picks the lowest-cost
non-overlapping set of patterns for the strength score.

## Data source
- Leaked passwords: SecLists `xato-net-10-million-passwords-1000000.txt` (top 1M by frequency, MIT licence).
- Dictionaries: Google 10,000 English words (no swears), SecLists first names, and generated keyboard walks and years.
- Organisations: a seeded synthetic company ("Kestrel Labs", 240 accounts, 771 access edges) generated by `OrgDemoGenerator`, in `data/org-demo/`. Real organisations' password exports are not available and must never be fabricated as real.

## Measurable success criteria
| Criterion | Target |
|---|---|
| False negatives (a leaked password reported safe) | 0 across all 1M leaked passwords |
| Measured Bloom FPR vs target 1% | Within ±20% of the theoretical rate |
| Disk reads with Bloom precheck vs disk-only | At least 5× fewer on a 95% non-leaked query mix |
| Trie vs naive scan, full dictionary | At least 50× faster, with identical matches |
| Single-password audit latency | Under 5 ms server-side |
| Correctness tests | At least 5 per core algorithm, including edge cases |
| Min cut vs brute force over every subset | Equal on all random graphs with up to 10 accounts |
| Best-first vs brute-force guessing, 5M guesses | Cracks at least 10× more synthetic accounts |
| Repeat filter memory vs HashSet, 2M guesses | At least 20× less, under 0.1% new guesses wrongly skipped |
| Attack simulation on the 240-account demo | Under 5 s end to end |
