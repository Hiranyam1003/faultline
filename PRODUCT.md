# Product

## Platform

web

## Users
Three audiences carry equal weight:
- **College or company IT administrators** auditing an exported password list (one per line, or `username,password` CSV, up to 10,000 rows) before a policy rollout.
- **Individual users** checking one password before they use it, and wanting to know *why* it is weak, not just a coloured bar.
- **Faculty evaluators** grading the CIA 3 Advanced Algorithm project, who need to see each assessed algorithm (Bloom filter, trie, KMP) doing real work and explained.

## Product Purpose
Faultline checks passwords against 1 million real leaked passwords and explains what makes them guessable. For an organisation, it simulates an attacker cracking every account and names the fewest accounts to secure so a chosen system (e.g. Payroll DB) is out of reach. It breaks a password into the pieces an attacker would try first (dictionary words, names, years, keyboard walks, leetspeak, the username, repeated blocks), scores it 0–4 with an entropy estimate, and gives concrete advice. It does this for a single password or a batch file. Success means it never reports a leaked password as safe, answers fast, and makes the reasoning visible.

## Positioning
Every algorithm is hand-written Java and shown working: the Check page draws the SHA-1 and the 7 Bloom bit positions it probed, separates "possibly leaked" (Bloom hit) from "confirmed, rank #N" (exact binary search), and can demonstrate a live false positive (`bluefox136`). The benchmarks page measures each algorithm against a baseline. It explains the result rather than just showing a strength meter. The attack simulation turns the audit into an operational decision: a best-first cracking race (binary heap) times when each account falls, and max-flow min-cut (Edmonds–Karp) on the access graph names the smallest set of accounts to secure, with the time to reach the target before and after.

## Operating Context
- Built for the CIA 3 Advanced Algorithm project (Semester V, B.Tech CS AI & ML, 2026–27). It will be **presented live in a demo/viva**, on a projector to a room.
- Runs locally: backend on `localhost:8080`, frontend on `localhost:5173` proxying `/api`.
- Pages: Check, Batch, Simulate an attack, Redact secrets, Benchmarks, How it works.
- Faculty feedback (Nov 2026) was that the first version "felt like a game, not a useful thing"; the attack simulation was added to answer it.

## Capabilities and Constraints
- Backend: Java 21+, Spring Boot, REST API (`POST /api/audit`, `POST /api/audit/batch`, `GET /api/stats`, `POST /api/benchmark`). No database; a sorted 24 MB binary hash file on disk.
- Frontend: React + Vite with **plain CSS and no UI library** (binding).
- The browser does no algorithm work; it calls the Java API and displays the results.
- A Bloom hit is only "possibly leaked"; only the exact check reports a breach. False negatives are impossible.
- The strength score is a simplified guess-count estimate, not a guarantee.
- Passwords go only to the local server and are never written to disk or logs. Batch results show masked passwords only.
- Input validation: empty, whitespace-only, over 128 characters, control characters, over-long username; empty, oversized (>1 MB), non-UTF-8 or over-10,000-row files; malformed CSV rows reported per line.
- Terminology: "possibly leaked" vs "confirmed"; "Bloom false positive"; leak rank; patterns; score 0–4 with verdict.

## Evidence on Hand
- Benchmarks in `docs/benchmarks.md`: Bloom FPR 0.98% against 1.00% theory at n = 1M, using 1.2 MB against about 85 MB for a HashSet; Bloom + disk 17× faster with 18× fewer disk reads; trie 42×–698× faster than a naive scan; KMP up to 324× faster on worst-case input.
- 95 JUnit tests, including a full 1M no-false-negative check and min cut vs brute force on random graphs.
- Synthetic demo organisation (Kestrel Labs, 240 accounts) in `data/org-demo/`, generated by `OrgDemoGenerator`; label it synthetic wherever it appears.
- Screenshots in `docs/screenshots/`; demo and ad videos in `docs/`.
- Data: SecLists top 1M leaked passwords and names, Google 10,000 English words (attributions in README).
- Team names in `docs/proposal.md` are still placeholders. Do not invent them, or any users, testimonials or adoption claims.

## Product Principles
1. Never imply safety you can't prove: keep "possibly leaked" and "confirmed" visibly distinct.
2. Explain why: every verdict shows the pieces and the reasoning behind it.
3. Make the algorithms visible: evaluators should see the Bloom filter, trie, KMP, Aho–Corasick, heap and max-flow doing real work.
4. End in a decision: an organisation-level result should tell IT what to do next, not just what is wrong.
5. Serve the admin, the individual and the evaluator without hiding any of them.
6. Legible live: everything must read clearly on a projector during a demo.
